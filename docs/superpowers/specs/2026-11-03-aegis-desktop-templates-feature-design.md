# Aegis Desktop — Templates Feature Design

## Goal

Add a **Templates** feature to `apps/desktop/aegis-desktop`. Admins curate the
global folder-structure templates that projects inherit; every other
authenticated user can read them.

Two pages:

1. **Templates** (`/templates`) — a landing page under the *Knowledge Base*
   menu. It shows one card today: *Standard Project Folder Structure*. Clicking
   it opens the structure template page. The card's title and blurb are **fixed
   text in the frontend** — they do not come from the API.
2. **Project Structure Template** (`/templates/structure/$structureId`) — a
   right sidebar listing the template-level structures from
   `GET /api/structures?level=template`, and a tree pane on the left showing the
   selected structure's folder structure in two interchangeable views
   (*Complete* and *Flat*). Admins (role `root` or `admin`) get add / edit /
   delete affordances on every node; general users get a read-only tree.

The scope is **desktop-only**. The server already ships every endpoint this
feature needs (`apps/server/aegis-server/src/transport/http/structures/`), and
nothing in `apps/server` or `lib/crates` changes.

## Architecture

```
  React (features/templates)
        │  invoke("list_structures", …)
        ▼
  Tauri commands (src-tauri/src/commands/structures.rs)   ← 1:1 shim
        │
        ▼
  HTTP client  (src-tauri/src/http/structures.rs)          ← wire DTOs
        │  GET/POST/PUT/DELETE /api/structures/…
        ▼
  aegis-server (unchanged)
```

### The tree widget

`@mui/x-tree-view` is **not** in the workspace today, and `@aegis/ui` ships only
a `Sidebar`. The package is added the same way `@mui/x-charts` already is:

- `lib/packages/ui/package.json` → `"@mui/x-tree-view": "9.16.0"` as a regular
  dependency (not a peer), so it resolves the *same* `@mui/material` instance as
  the rest of the app — a second instance would put the tree on a different
  theme context.
- `lib/packages/ui/src/tree-view/index.ts` → `export * from '@mui/x-tree-view';`
- `lib/packages/ui/package.json` `exports` → `"./tree-view": "./src/tree-view/index.ts"`.

The desktop then imports `import { SimpleTreeView, TreeItem } from "@aegis/ui/tree-view";`
and never takes a direct `@mui/*` dependency.

`9.16.0` is the pin because it is the version already used for `@mui/x-charts`,
and its peer range (`@mui/material: ^7.3.0 || ^9.0.0`, `react: ^19`) matches the
workspace's `@mui/material@9.2.0` and `react@19`.

### Why these approaches

| Decision | Chosen | Alternatives rejected |
| --- | --- | --- |
| Where the HTTP call lives | New Tauri transport (`http/structures.rs` + `commands/structures.rs`) | Calling the server from TS with `fetch` — breaks CLAUDE.md's "Rust side is transport-only" rule and loses `HttpClient`'s token-refresh handling. |
| Tree implementation | `@mui/x-tree-view` (`SimpleTreeView` + `TreeItem`) | A hand-rolled nested `List`/`Collapse` — no new dependency, but no keyboard navigation, no expand/collapse state management, and no ARIA tree semantics. The user chose the real tree widget. |
| How the two views share data | One `get_structure` fetch; *Flat* is a pure client-side transform of that tree | A second endpoint — the server has no flat view and server changes are out of scope; a second request would also let the two views disagree. |
| Where the sidebar's selection lives | Path param `$structureId` | Local component state — not deep-linkable, and the back button would leave the page instead of stepping through templates. |
| How the card reaches the structure | `/templates/structure` with no preselection; the page auto-selects the first template structure | Hardcoding the structure *name* in the card and matching it in the sidebar — breaks if the structure is renamed in the DB. |

### The two views

Both views are rendered from the **same** `StructureView.nodes` array returned by
`get_structure`. The server already omits hidden nodes and their whole subtree
from that array, and it rejects `hidden = true` against a template structure
outright — so "filter out the hidden nodes" is the server's job and the
desktop renders exactly what it receives. There is no `hidden` field on the
tree DTO to filter client-side.

**Complete view** — the tree exactly as the API returns it: nodes nested by
`parent`, roots at the top.

**Flat view** — a pure transform of the same tree:

- Every **directory** node, at any depth, becomes a **top-level entry**.
- A sub-directory is **never nested under its parent**; it gets its own
  top-level entry.
- The **files** directly inside a directory become that directory entry's
  leaves.
- A directory entry shows its **full path** (the path of the directory itself
  relative to the structure root, e.g. `raw/data`) — the extra path display the
  spec asks for in the flat view.
- A **file** at the root (no parent) has no directory to sit under, so it
  becomes its own top-level entry. *(Builder's call — the spec does not cover
  it.)*

`path` on a node is the node's path **relative to the structure root**
(`raw/a.txt`). The server does not require a node's `path` to lie inside its
parent's `path` — the tree is defined by the `parent` links — so the full path
shown in the flat view is the node's own `path`.

### The path the desktop owns

The structures spec is explicit: *"the `path` is the relative path the caller
records, and the desktop app owns computing it."* The server never derives a
child's path from its parent.

So when the admin adds a node under a parent, the drawer **prefills** the path
field with `<parent.path>/` and the admin completes the last segment. Adding at
the root leaves the field empty. On edit, the field shows the node's current
`path` unchanged. The admin may still edit the whole path — it is a free-text
field, and the server validates it.

```
┌──────────────────────────────────────────┬──────────────────────────┐
│  Structure name     [Complete|Flat]      │  Structures              │
│  ────────────────────────────────────────│  ────────────────────────│
│  + Add root node                         │  ┌────────────────────┐  │
│                                          │  │ Standard Project   │  │
│  v raw                                   │  │   Folder Structure │  │
│      Statistical programming raw         │  ├────────────────────┤  │

│      > raw/adam                          │                          │
└──────────────────────────────────────────┴──────────────────────────┘
```

**Sidebar (right).** `GET /api/structures?level=template`, showing each
structure's `name`. The selected one is highlighted; clicking navigates to
`/templates/structure/$structureId`.

**Tree pane (left).** The structure name, a *Complete* / *Flat* toggle, and the
tree.

**Node row.** The node's `path` as the primary label. Below it, in secondary
text:

- `description` — always, when non-empty.
- `reference` — files only (the server rejects `reference` on a directory).
- `migration` — directories only: the migration `directory`, plus its `filter`
  list. (The server rejects `migration` on a file.)

**Admin affordances.** For `root` and `admin` roles only:

- Every node row gets a trailing tool icon (`MoreHoriz`). Clicking it opens a
  menu with the three actions — **add** (opens the add drawer with this node as
  the parent), **edit** (opens the drawer on this node), **delete** (opens the
  confirm dialog). The spec calls these "a list of icon buttons"; they are
  rendered as a menu whose entries carry an action icon **and** a text label,
  because a bare icon button in a menu is not reachable by name. *(Builder's
  call.)*
- Above the tree, a **root add** button opens the add drawer with
  `parent = null`, creating a first-level node.

General users see no icons and no buttons — the tree is read-only.

## Node editing

One drawer serves add and edit.

| Field | Applies to | Notes |
| --- | --- | --- |
| `path` | all | Required. Prefilled `<parent.path>/` on add-under-parent; empty on add-at-root; the current value on edit. |
| `description` | all | Free text. May be empty. |
| `directory` | all | Switch. Folder vs file. |
| `reference` | files only | Absolute file path. The field is hidden when `directory` is true. |
| `migration.directory` | directories only | Source directory to copy from. Hidden when `directory` is false. |
| `migration.filter` | directories only | List of filter strings. |

**No `hidden` field.** `hidden` is only meaningful at project level — the
server rejects `hidden = true` against a template structure with a `400`, and
a hidden node is already absent from the tree the page renders. So the drawer
omits the field and the client never sends it.

**`parent` is always sent.** `AddNodeRequest` / `UpdateNodeRequest` are full
replacements and `parent` is always explicit (`null` means "at the root"), so
the drawer sends the parent's `nodeId` on add and the node's existing `parent`
on edit. Omitting it would silently re-parent the node.

**Client-side validation** mirrors the server's `validate_path`:

- non-blank, no leading or trailing `/`, no `\`, no empty / `.` / `..` segment.

The Save button is disabled while the path is invalid, with the reason shown
under the field.

### Delete

A confirm dialog naming the node by `path`: *"Delete `raw/data` and everything
under it?"* Confirming calls `DELETE /api/structures/{id}/nodes/{node_id}`,
which answers `204` with an empty body — the desktop adapter must not try to
JSON-decode it (the same trap `http/mission.rs::remove_assignee` documents).

## Data layer

### Wire types (TS mirror of the server DTOs)

```ts
export type StructureLevel = "template" | "project";

export interface MigrationView {
  directory: string;
  filter: string[];
}

export interface StructureNodeView {
  nodeId: string;
  description: string;
  path: string;
  directory: boolean;
  parent: string | null;
  reference: string | null;
  migration: MigrationView | null;
  children: StructureNodeView[];
}

export interface StructureView {
  id: number;
  name: string;
  level: StructureLevel;
  projectCode: string | null;
  templateId: number | null;
  nodes: StructureNodeView[];
}

export interface StructureSummaryView {
  id: number;
  name: string;
  level: StructureLevel;
  projectCode: string | null;
  templateId: number | null;
}

export interface StructureNodeInput {
  path: string;
  description: string;
  directory: boolean;
  parent: string | null;
  reference: string | null;
  migration: MigrationView | null;
}
```

The Rust side declares the same shapes with `#[serde(rename_all = "camelCase")]`,
mirroring `apps/server/aegis-server/src/transport/http/dto.rs` §structures.
`StructureLevel` serialises as `"template"` / `"project"`.

### Endpoints used

| Desktop call | Server route |
| --- | --- |
| `list_structures(level=template)` | `GET /api/structures?level=template` |
| `get_structure(id)` | `GET /api/structures/{id}` |
| `add_node(structureId, body)` | `POST /api/structures/{id}/nodes` |
| `update_node(structureId, nodeId, body)` | `PUT /api/structures/{id}/nodes/{node_id}` |
| `delete_node(structureId, nodeId)` | `DELETE /api/structures/{id}/nodes/{node_id}` |

`list_structures` returns a `StructureListResponse { structures: [...] }`; the
desktop adapter unwraps it to a plain array before it crosses into TS, exactly
as `http/mission.rs::list_by_project` does.

The server's read routes need only a valid token; the write routes need
`admin` or `root` **because the target is a template structure**
(`require_template_write_permission`). The desktop additionally hides the
affordances from general users, so a general user never sees a 403.

### Query keys

```ts
structures: {
  list: (level: StructureLevel) => ["structures", "list", level] as const,
  detail: (id: number) => ["structures", "detail", id] as const,
},
```

The three node mutations invalidate `structures.detail(id)` and
`structures.list("template")` on success.

## Routes

```
src/routes/_authed/_layout/templates.tsx                    → /templates
src/routes/_authed/_layout/templates/structure/index.tsx     → /templates/structure
src/routes/_authed/_layout/templates/structure/$structureId.tsx → /templates/structure/$structureId
```

The `index.tsx` route renders the same page component with `structureId =
null`. When the template list loads and no structure is selected, the page
navigates to `/templates/structure/$structureId` for the first structure with
`replace: true`, so the URL settles on a shareable link. The `$structureId`
route passes its param to the same component.

Both structure routes render `StructureTemplatePage`, which takes the selected
id as a prop — the component never reaches into the router for the param.

## Goals / non-goals

**Goals**

- Admins can add, edit and delete nodes of a global template structure.
- Everyone authenticated can read the template structures and their trees.
- Both tree views render from one fetch.
- The card list and the whole UI are bilingual (en / zh-CN).

**Non-goals**

- Creating, renaming or deleting *structures* — the spec's scope is nodes.
  A template structure is created out of band.
- Project-level structures. Only `level=template` is listed and only template
  structures are editable here.
- Node reordering by drag-and-drop.
- The `hidden` affordance (rejected by the server for templates).
- The `list_own_nodes` endpoint — the page renders the effective tree, and
  hidden nodes are project-level only.
- Any change to `apps/server` or `lib/crates`.

**Anti-goals**

- No direct server calls from TypeScript.
- No second copy of the wire DTOs — the Rust and TS halves are hand-mirrored,
  as the repo requires, and both change in the same commit.

## Testing

**Rust** (`src-tauri/src/http/structures.rs`) — serde shape tests mirroring
`http/mission.rs`: the level enum serialises lowercase, a node view parses the
full wire shape, a request round-trips. Plus a `wiremock` test that
`delete_node` succeeds on a `204` with no body.

**Rust** (`src-tauri/src/commands/structures.rs`) — the `_impl` twins are
callable without a Tauri runtime, so a fake `HttpClient` can assert the
command maps its arguments onto the right URL.

**TypeScript** (`src/test/features/templates/`):

- `data/tree.test.ts` — the flat transform: a sub-directory is **not** nested
  under its parent; a directory's files are its leaves; a root-level file is a
  top-level entry; the full path is carried.
- `templates-page.test.tsx` — the card renders the fixed title and content.
- `structure-template-page.test.tsx` — the sidebar lists the template
  structures by name; the tree renders; a general user sees no action icons;
  an admin sees them.
- `node-drawer.test.tsx` — the reference field shows only for files, the
  migration fields only for directories, `parent` is sent on save, an invalid
  path disables Save.

Frontend tests live in `src/test/features/<feature>/`, mirroring the feature
module name — the existing convention.

## Open items

None that block the build. Both open items were settled in the implementation
plan (`docs/superpowers/plans/2026-11-03-aegis-desktop-templates-feature.md`):

1. The flat view's "full path" is the node's own `path`. The server does not
   enforce that a node's `path` lies inside its parent's `path`, so the two can
   disagree in principle; the spec says the desktop owns the path, so the
   node's own `path` is used. The flat view shows the directory by its **name**
   (the last segment) plus that full path.
2. The exact wording of the two card strings and of the delete confirmation is
   pinned by the i18n catalog in the plan.
