# Project Branch Design

## Goal

Add a **project branch** to the `project` lib crate: a named working branch
that a clinical data project owns over time, of which at most one is *active*
at any moment. The active branch decides the working directory for the
project's members.

The branch ships as:

- A `project_branches` table (one migration in the `project` crate).
- A `ProjectBranch` domain model + `ProjectBranchRepository` port in the
  crate's `domain` layer.
- A `ProjectBranchUsecase` in the crate's `usecase` layer.
- A `ProjectBranchRepo` Postgres adapter in the crate's
  `adapter/persistence/postgres` layer.
- Four methods on the existing `apis::project::ProjectService` port, plus the
  `ProjectBranchView` / `CreateProjectBranchRequest` /
  `UpdateProjectBranchRequest` DTOs in `apis::project`.
- Four HTTP routes under `/api/project/{code}/branches` in `aegis-server`.

The desktop app is **not** touched: no TS types, no API client, no UI.

## Scope

| In | Out |
| --- | --- |
| `project_branches` table + migration | Deleting a branch (no DELETE route, no repo method) |
| `ProjectBranch` domain model, port, usecase | Branch list inside `ProjectView` |
| Four `ProjectService` methods for branches | Any desktop change (`apps/desktop/aegis-desktop` untouched) |
| Four HTTP routes under `/api/project/{code}/branches` | Working-directory paths, period start/end dates |
| Live-DB integration tests for the new table | Pagination on the list route |
| | Branch membership (who is on which branch) |

## Terminology

- **Branch** — a named working line inside one project. The name is a plain
  label (`"2026Q1"`, `"pre-lock"`); nothing about the filesystem is stored.
- **Active branch** — the one branch of a project that is currently in effect.
  At most one branch of a project is active at a time.
- **Switch** — the act of making branch B active. B becomes active *and* the
  previously active branch A is deactivated, in one transaction.

## Decisions

These were settled with the requester and are the load-bearing parts of the
design.

1. **Activation is a switch, not a flag set.** Activating B deactivates A in
   the same transaction. The caller does not deactivate A first, and a
   conflict is never reported for "another branch is active".
2. **Branches are a standalone resource.** `ProjectView` does **not** gain a
   `branches` field. The project payload is unchanged, so the desktop's
   hand-written mirror of the Rust DTOs stays valid.
3. **The branch name is unique within its project.** Two branches of the
   same project cannot share a name; different projects may each have a
   `"2026Q1"`.
4. **A project may have zero branches.** Creating a project does not
   auto-create a branch. "At most one active" is the rule, not "exactly one".
5. **Branches are never removed.** Create, read, list, rename and
   activate/deactivate exist; delete does not. There is no DELETE route and
   no `delete` on the repository port.
6. **Activation rides on the update request.** `PATCH` with `{"active": true}`
   — not a dedicated `/activate` route.
7. **The branch methods fold into `ProjectService`.** `apis::project::ProjectService`
   gains four branch methods rather than a new `apis::project_branch` module.
   The server's `AppState` is unchanged.

## Data model

```sql
CREATE TABLE project_branches (
    id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    project_id INTEGER NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    branch TEXT NOT NULL,
    active BOOLEAN NOT NULL DEFAULT FALSE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CONSTRAINT project_branches_branch_unique UNIQUE (project_id, branch),
    CONSTRAINT project_branches_branch_not_empty CHECK (length(btrim(branch)) > 0)
);

CREATE UNIQUE INDEX project_branches_one_active_per_project
    ON project_branches (project_id) WHERE active;
```

plus a `project_branches_set_updated_at` `BEFORE UPDATE` trigger mirroring the
existing `projects_set_updated_at`.

Notes:

- `project_id` cascades on delete, so removing a project removes its
  branches. The project table has no hard-delete path today, so this is
  belt-and-braces.
- The **partial unique index** is the database-level backstop for "at most one
  active branch per project". The application enforces the same rule inside
  a transaction; the index catches anything that reaches the table by
  another route.
- `branch` is a non-reserved word in PostgreSQL and needs no quoting.
- The `CHECK` on `length(btrim(branch)) > 0` rejects a blank name even if a
  row is inserted by direct SQL.

The migration file is created by the sqlx CLI, never by hand:

```bash
sqlx migrate add --source lib/crates/project/migrations --timestamp create_project_branches
```

## Domain layer

New module `src/domain/project_branch.rs`:

```rust
pub struct ProjectBranch {
    pub id: i32,
    pub project_id: i32,
    pub branch: String,
    pub active: bool,
    pub created_at: DateTime<Utc>,
    pub updated_at: DateTime<Utc>,
}
```

with the two constructors the guideline requires:

- `ProjectBranch::new(id, project_id, branch, active, created_at, updated_at)
  -> Result<Self, DomainError>` — the validating constructor. Rejects a name
  that is empty or whitespace-only with `DomainError::EmptyBranchName`.
- `ProjectBranch::for_repository(...) -> Self` — `pub(crate)`, bypasses
  validation, used by the row bridge.

Input DTOs for the port:

```rust
pub struct ProjectBranchNew {
    pub project_id: i32,
    pub branch: String,
    pub active: bool,
}

pub struct ProjectBranchUpdate {
    pub id: i32,
    pub project_id: i32,
    pub branch: Option<String>,
    pub active: Option<bool>,
}
```

### The port

```rust
#[async_trait]
pub trait ProjectBranchRepository: Send + Sync {
    async fn create(&self, input: ProjectBranchNew) -> Result<ProjectBranch, DomainError>;
    async fn find_by_id(&self, id: i32) -> Result<ProjectBranch, DomainError>;
    async fn list_by_project(&self, project_id: i32) -> Result<Vec<ProjectBranch>, DomainError>;
    async fn update(&self, input: ProjectBranchUpdate) -> Result<ProjectBranch, DomainError>;
}
```

The switch is a **cross-row** invariant, so it cannot live in the domain
constructor or in a single-row `UPDATE`. It is therefore part of the port's
contract, documented on the trait:

- `create` with `active: true` — deactivates every currently-active branch
  of `project_id`, then inserts the new branch as active. One transaction.
- `update` with `active: Some(true)` — deactivates every *other* active
  branch of the branch's project, then sets this one active. One transaction.
- `update` with `active: Some(false)` — sets this branch inactive. The
  project is then left with no active branch, which is legal.
- `update` with `active: None` — leaves the flag alone.
- `update` with `branch: Some(name)` — renames. A name that collides with
  another branch of the same project surfaces as
  `DomainError::DuplicateBranch`.

### Domain errors

Added to `DomainError`:

- `EmptyBranchName` — "branch name must not be empty".
- `DuplicateBranch(String)` — "branch already exists: {0}" (unique violation
  on `(project_id, branch)`). The payload is the **branch name the caller
  asked for**, not the driver's wording.
- `BranchNotFound(i32)` — "branch not found: {0}".
- `BranchProjectNotFound(i32)` — "branch project not found: {0}" (the
  branch's owning project does not exist; a foreign-key violation).

## Usecase layer

New module `src/usecase/project_branch_usecase.rs`:

```rust
pub struct ProjectBranchUsecase<B: ProjectBranchRepository> {
    branches: B,
}
```

Methods:

| Method | Behaviour |
| --- | --- |
| `create_branch(cmd)` | Validates the name, calls `repo.create`. |
| `get_branch_by_id(id)` | Calls `repo.find_by_id`. |
| `list_branches(project_id)` | Calls `repo.list_by_project`. |
| `update_branch(cmd)` | Validates the name when present, calls `repo.update`. |

Command DTOs live in `usecase/commands.rs`:

```rust
pub struct CreateProjectBranch {
    pub project_id: i32,
    pub branch: String,
    pub active: bool,
}

pub struct UpdateProjectBranch {
    pub id: i32,
    pub branch: Option<String>,
    pub active: Option<bool>,
}
```

Validation rules (surfaced as `UsecaseError::Validation`, not `Repository`):

- `create`: the name is trimmed and must be non-empty afterwards.
- `update`: when `branch` is `Some`, the name is trimmed and must be
  non-empty afterwards.

The **trimmed** name is what reaches the repository, so `" 2026Q1 "` is
stored as `"2026Q1"`.

The view DTO is `usecase::ProjectBranchView`, mirroring the domain struct
minus nothing — it carries `id`, `project_id`, `branch`, `active`,
`created_at`, `updated_at`.

`ProjectUsecase` is **not** touched. The branch aggregate has its own
lifecycle and its own usecase.

## Adapter layer — persistence

New file `src/adapter/persistence/postgres/branch_repo.rs` with
`ProjectBranchRepo { pool: PgPool }`, implementing `ProjectBranchRepository`.
The row bridge `ProjectBranchRow` goes next to `ProjectRow` in
`postgres/row.rs`.

SQL notes:

- `create` runs in a transaction: when `active` is true it first issues
  `UPDATE project_branches SET active = FALSE WHERE project_id = $1 AND active`,
  then inserts the row with `active = true`, then commits.
- `update` runs in a transaction: the rename and the active flag are applied
  in the same statement batch, and the sibling deactivation happens in the
  same transaction when the flag is set to true.
- The unique-violation mapping is specialised: SQLSTATE `23505` on the
  `project_branches_branch_unique` constraint maps to
  `DomainError::DuplicateBranch(name)`; any other unique violation keeps the
  existing `DomainError::DuplicateCode` behaviour.
- `sqlx::Error::RowNotFound` maps to `DomainError::NotFound`; the branch
  lookup wrapper converts that into `DomainError::BranchNotFound(id)`.

## Adapter layer — facade

`ProjectServiceImpl` gains a third generic parameter and a second usecase:

```rust
pub struct ProjectServiceImpl<R, U, B>
where
    R: ProjectRepository,
    U: UserService,
    B: ProjectBranchRepository,
{
    usecase: ProjectUsecase<R, U>,
    branch_usecase: ProjectBranchUsecase<B>,
}

impl<R, U, B> ProjectServiceImpl<R, U, B> {
    pub fn new(usecase: ProjectUsecase<R, U>, branch_usecase: ProjectBranchUsecase<B>) -> Self
}
```

The four new `ProjectService` methods delegate to `branch_usecase` and map
`UsecaseError` onto `ProjectApiError` through the existing `map_error`
helper, extended with the two new branch variants.

## The `apis` contract

All new types live in the existing `apis::project` module.

```rust
pub struct ProjectBranchView {
    pub id: i32,
    pub project_id: i32,
    pub branch: String,
    pub active: bool,
    pub created_at: DateTime<Utc>,
    pub updated_at: DateTime<Utc>,
}

pub struct CreateProjectBranchRequest {
    pub project_id: i32,
    pub branch: String,
    pub active: bool,
}

pub struct UpdateProjectBranchRequest {
    pub id: i32,
    pub project_id: i32,
    pub branch: Option<String>,
    pub active: Option<bool>,
}
```

`CreateProjectBranchRequest.active` is a plain `bool`. An absent field on
the wire means "not active"; there is no third state to express, so the
`Option` would carry no information.

The port gains four methods:

```rust
async fn create_project_branch(
    &self,
    req: CreateProjectBranchRequest,
) -> Result<ProjectBranchView, ProjectApiError>;

async fn get_project_branch_by_id(
    &self,
    id: i32,
) -> Result<ProjectBranchView, ProjectApiError>;

async fn list_project_branches(
    &self,
    project_id: i32,
) -> Result<Vec<ProjectBranchView>, ProjectApiError>;

async fn update_project_branch(
    &self,
    req: UpdateProjectBranchRequest,
) -> Result<ProjectBranchView, ProjectApiError>;
```

New `ProjectApiError` variants:

- `DuplicateBranch(String)` — 409, wire code `duplicate_branch`.
- `BranchNotFound(i32)` — 404, wire code `branch_not_found`.
- `BranchProjectNotFound(i32)` — 404, wire code `branch_project_not_found`.

Adding methods to `ProjectService` is a breaking change for every
implementation of the trait. In this repository that means updating:

- `project::ProjectServiceImpl` (the real one).
- The server's `MockProjectService` (`transport/http/project/handlers.rs`).
- The server's `NullProjectService` (`transport/http/state.rs`).
- The server's `NullProjectService` (`transport/http/router.rs`).

## Server HTTP surface

Four routes, registered in `transport/http/project/router.rs`:

| Method | Path | Auth | Success |
| --- | --- | --- | --- |
| `POST` | `/api/project/{code}/branches` | admin / root | 201 + branch view |
| `GET` | `/api/project/{code}/branches` | any authenticated | 200 + `{ "branches": [...] }` |
| `GET` | `/api/project/{code}/branches/{id}` | any authenticated | 200 + branch view |
| `PATCH` | `/api/project/{code}/branches/{id}` | admin / root | 200 + branch view |

Auth policy mirrors the existing project routes: reads are open to any
authenticated caller, writes go through `require_admin_or_root`.

Handler behaviour:

- `{code}` is resolved to a project id through
  `state.project.get_project_by_code(&code)`. An unknown project is a 404
  (`not_found`) on every route.
- `GET`/`PATCH` by `{id}` verify the branch belongs to the resolved project.
  A branch that exists but belongs to another project is a 404
  (`branch_not_found`) — the caller named a resource that is not there.
- `PATCH` accepts `{"branch": "...", "active": true}` and applies both.
- The wire DTOs (`CreateProjectBranchRequest`, `UpdateProjectBranchRequest`,
  `ProjectBranchViewResponse`, `ProjectBranchListResponse`) are added to
  `transport/http/dto.rs` with `camelCase` JSON names. The response DTOs
  mirror the apis view field-for-field; the *request* DTOs deliberately
  do not — the project and branch ids arrive in the URL, so the wire
  create body carries only `branch` and `active`, and the wire update
  body only `branch` and `active`. The handler fills the ids in.

The `OpenAPI` document gains the four routes; the router-level test asserts
each advertises `BearerAuth`, that the two writes advertise a 403 and the
two reads do not.

## Error mapping

| Situation | Domain | apis | HTTP | wire code |
| --- | --- | --- | --- | --- |
| Blank branch name | `EmptyBranchName` | `Validation` | 400 | `validation_failed` |
| Name collides in the project | `DuplicateBranch` | `DuplicateBranch` | 409 | `duplicate_branch` |
| Unknown branch id | `BranchNotFound` | `BranchNotFound` | 404 | `branch_not_found` |
| Unknown owning project | `BranchProjectNotFound` | `BranchProjectNotFound` | 404 | `branch_project_not_found` |
| Unknown project code | `NotFound` | `NotFound` | 404 | `not_found` |
| Caller is not admin/root | — | — | 403 | `forbidden` |
| No bearer | — | — | 401 | `token_verification_failed` |
| Driver failure | `Repository` | `Repository` | 500 | `repository_error` |

## Tests

Following the guideline's test-tier order:

1. **Domain** (`src/domain/tests.rs`) — `ProjectBranch::new` rejects an empty
   and a whitespace-only name; `for_repository` bypasses the check.
2. **Adapter unit** (`src/adapter/persistence/postgres/tests.rs`) — the
   `ProjectBranchRow` → `ProjectBranch` conversion, and a read of the
   migration file asserting the column set, the unique constraint, the
   partial unique index, the `CHECK` and the trigger.
3. **Usecase unit** (`src/usecase/tests.rs`) — an in-memory
   `ProjectBranchRepository` fake; create with a blank name is a validation
   error; create / get / list / update happy paths; the trimmed name
   reaches the repository.
4. **Facade unit** (`src/adapter/facade/internal/tests.rs`) — the facade
   over the in-memory fake, end-to-end through the apis port, including
   `Box<dyn ProjectService>` object-safety.
5. **public_api compile-only** (`tests/public_api.rs` in both `project` and
   `apis`) — name the new public types, the new `DomainError` and
   `ProjectApiError` variants, and update the pinned
   `ProjectServiceImpl<ProjectRepo, UserServiceImpl>` signature to
   `ProjectServiceImpl<ProjectRepo, UserServiceImpl, ProjectBranchRepo>`.
6. **integration_persistence** (`tests/integration_persistence.rs`,
   `#[ignore]`-gated) — create a branch; a duplicate name in the same
   project fails; the same name in a *different* project succeeds;
   activating B deactivates A; listing shows the switch; renaming works.
   The live-DB env var is `AEGIS_DATABASE_URL` (the workspace-shared one this
   crate's existing integration test already reads), and the test drops
   `project_branches` (and its dependencies) before each run.
7. **Server handler tests** (`transport/http/project/handlers.rs`) — the
   success paths, 401 without a bearer, 403 for a `General` writer, 404 for
   an unknown project / unknown branch / branch of another project, 409 for
   a duplicate name, 400 for a blank name.

## Wiring

`aegis-server`'s `run.rs` builds the branch repository alongside the project
repository and hands it to the facade:

```rust
fn build_project_service(
    pool: PgPool,
    user: Arc<dyn apis::user::UserService>,
) -> Arc<dyn apis::project::ProjectService> {
    let project_repo = project::ProjectRepo::new(pool.clone());
    let branch_repo = project::ProjectBranchRepo::new(pool);
    let users = project::UserServiceImpl::new(user);
    let usecase = project::ProjectUsecase::new(project::ProjectUsecaseConfig {
        project_repo,
        users,
    });
    let branch_usecase = project::ProjectBranchUsecase::new(branch_repo);
    Arc::new(project::ProjectServiceImpl::new(usecase, branch_usecase))
}
```

`AppState` is unchanged — the branch methods live on the existing
`project` service.

## Calls I made

These were not settled in the conversation; they are my calls, recorded here
so they can be overridden.

- **`created_at` / `updated_at` on the branch.** The starting data model in
  the request listed only `id`, `project_id`, `branch`, `active`. I added
  the two timestamps because guideline §8 asks for auto-managed timestamps on
  every table and every other entity in the crate carries them. Dropping them
  later is one migration plus a field removal.
- **Trimmed names.** The stored name is the trimmed name; a whitespace-only
  name is a validation error.
- **A dedicated `BranchNotFound` error** rather than reusing the generic
  `NotFound`, so the wire code says which resource was missing — matching the
  `crf` / `sdtm_project` / `structures` crates.
- **A dedicated `BranchProjectNotFound` error** for a branch whose owning
  project does not exist, also matching the `crf` / `sdtm_project` crates'
  typed foreign-key errors. The `DuplicateBranch` payload is the branch name
  the caller asked for, not the driver's message.
- **Routes nested under `/api/project/{code}/branches`** rather than a
  top-level `/api/project-branch` namespace, because a branch is always
  reached through its project.
- **The branch gets its own usecase** (`ProjectBranchUsecase`) even though
  the apis port is folded into `ProjectService` — the branch has its own
  lifecycle, and keeping it out of `ProjectUsecase` avoids churning the
  existing usecase's generic parameters and test fakes.
- **No pagination** on the list route; a project has a handful of branches.

## Not in this change

- Deleting a branch. The repository has no `delete`; the HTTP surface has no
  DELETE route. Removing a branch later means adding both plus a decision
  about what happens to the project's active branch.
- The desktop app: no TS mirror of the new DTOs, no API client, no UI.
- Branch membership (which member sits on which branch).
- The working directory a branch maps to, and any period start/end dates.
- A "current branch" shortcut on the project payload — a caller that needs
  it reads `GET /api/project/{code}/branches` and picks the active one.
